# Arthas 阶段 0 实测报告

状态：8 项均已测量；项 5 中 JDK 11、21 上整个 JVM 暂停的原因未查明（3.5.6）；阈值建议中标为“估算”和“未验证”的值需要负责人确认。

- 对应计划：`docs/java-diagnostics-arthas-plan.md` 第 8 节“阶段 0”。
- 验证版本：测试代码的最后一个版本（本报告在其后）。在该版本上重新执行了 `python3 -m py_compile scripts/*.py`、`go build ./...`（`tools/`），以及对原始数据运行 `pause_seconds.py`、`pause_jdk11_gaps.py`、`pause_jdk17_phases.py`、`exp_iostall.py show`，输出与 3.5.6 的表一致。基准实验本身（`make bench` 约 3 小时）没有在该版本上重新运行：`bench.py` 的 `--sampler`、`--tripwire`，`ja.py`、`exp_planA.py` 的修改以及 `exp_iostall.py`、`stall_tripwire.py`、`pause_*.py` 在产生数据时尚未提交，提交的是数据产生结束后的版本，期间对这些脚本的中间修改未逐一记录。
- 原始数据和日志：保存在执行实测的本地主机上，大文件不进仓库。下文“原始数据”一列的路径都相对原始数据目录下的 `raw/`。
- 测试代码：`test/jvm-arthas/`，不含产品代码（`internal/`、`cmd/`、`api/`、`web/` 未改动）。

术语：

- p50、p99、p99.9：请求延迟的第 50、99、99.9 百分位。
- STW（stop-the-world）：JVM 暂停所有应用线程的操作，如 GC、`RedefineClasses`。
- 增强：Arthas 通过 `retransformClasses` 修改目标类字节码（计划第 4 节的 L2 命令）。
- cgroup 内存：容器内存控制组的 `memory.current`，包含匿名内存和页缓存。
- nspid：进程在其 PID 命名空间内的 pid。

## 1. 结论摘要

| 项 | 结论 | 覆盖 |
|---|---|---|
| 1 参数是否生效、密码是否写日志 | `password`、`localConnectionNonAuth=false`、`disabledCommands`、`sessionTimeout` 生效；`mcpEndpoint=` 在 Arthas 自带的 `arthas.properties` 存在时不生效，必须从包内属性文件删除 `arthas.mcpEndpoint`、`arthas.mcpProtocol`。密码未出现在 stdout、Arthas 日志、容器文件和 `/proc`。 | JDK 8/11/17/21 |
| 2 只有 JRE 的镜像 | 主机端 attach 可以运行 arthas-core，L1 命令全部成功；方案 A（arthas-boot）在 JRE 镜像中无法运行。缺少 `java.instrument` 模块的 jlink 运行时返回错误，目标不受影响。 | JRE 8、JRE 17、jlink 17 |
| 3 stop 后的回收；50 次 attach/stop | 线程（18→0）、监听端口回收，stop 后端口在 3.1~3.2 秒内关闭。每次 attach/stop 使元空间使用量增加约 12.1~12.7 MB（相邻两次循环的中位数）；类加载器需要 2 次 Full GC 才卸载，3 次 Full GC 后元空间使用量比基线高 7~10 MB。1 GB 内存限额的容器在完成 14~25 次循环后被 OOM killer 结束。 | JDK 8/11/17/21 |
| 4 会话超时、连接断开后的作业与增强 | `sessionTimeout` 只清理空闲会话，不终止正在运行的作业，也不还原增强。HTTP 客户端被杀死后作业继续到 `execTimeout`。作业结束、`execTimeout`、`close_session` 都不还原增强，只有 `reset` 或 `stop` 还原；作业运行期间先 `reset` 会使类残留增强。 | JDK 8/11/17/21（JDK 8/17 做了残留增强的恢复验证） |
| 5 对延迟的影响 | 没有 Arthas 调用的 60 秒窗口之间，合并 p99 的差异在 16 个比较中有 5 个超出 ±5%，60 秒窗口的合并 p99 不能分辨 5%。attach、命令、stop 所在秒的 p99 为基线（约 1.2 ms）的 1.2~3.2 倍（JDK 8 的 `classloader -t` 为 5.4 倍，该运行其他进程 CPU 偏高），最大延迟 8.8~24.5 ms；`thread -b` 为 8.9~14 倍，最大延迟 39~60 ms。L2 增强开始后的 1~4 秒，所有接口的最差一秒 p99 为 202~1209 ms，最大延迟 227~1446 ms，JVM CPU 178%~378%；`RedefineClasses` 安全点只有 15~41 ms。稳态（11 次安静运行）：未被观察接口的典型 p99 变化中位数 +3%（+2%~+15%）；被观察方法 1000 次/秒 +5%，10000 次/秒 +16%~+34%。JDK 11、21 上，10 次 `bench.py` 的 `l2:watch@p10k` 运行中有 3 次出现整个 JVM 的暂停，延迟 0.03~4.12 秒，影响所有接口；加 `--tripwire` 的 17 次 JDK 11 `l2:watch@p10k` 运行没有出现，原因未查明（3.5.6）。 | JDK 17 为主（35 次运行）；JDK 8：8 次；JDK 11、21：各 8 次 |
| 6 只读根文件系统、无 HOME | `.attach_pid` 必须创建在可写目录（`/tmp`）；Arthas 日志文件无法创建时不报错、不输出到 stdout，功能不受影响。 | JDK 8、17 |
| 7 已存在 Arthas 实例的检测 | 用线程名前缀 `arthas-` 加监听端口判断“正在运行”；已打开的 `arthas-*.jar` 文件描述符和内存映射在 stop 和 Full GC 后仍然存在，只能判断“曾加载过”。 | JDK 8/11/17/21 |
| 8 方案 A 的内存占用 | 方案 A 的容器内存峰值增量比主机端 attach 高 12~75 MB（两次运行，持续约 1.2~1.4 秒），稳定后增量不高于主机端 attach（两种方式执行的命令不同）。JDK 17 容器的内存限额 620m（650.1 MB，attach 前 519.8 MB）下方案 A 未 OOM，610m（639.6 MB）和 600m 下容器在方案 A 第 1 步中被 OOM killer 结束；主机端 attach 在 600m 下未 OOM。 | JDK 17（9 个限额）、JDK 8（1 个限额） |

## 3. 各项实测

### 3.1 项 1：agent 参数是否生效，密码是否写入日志

方法：按计划 3.1 的参数（`telnetPort=-1;httpPort=18563;ip=127.0.0.1;password=<随机>;localConnectionNonAuth=false;mcpEndpoint=;disabledCommands=<列表>;sessionTimeout=...`）attach，之后检查监听端口、认证行为、命令是否被禁用、密码是否出现在任何位置。另做 7 组参数变体（a~g）。

原始数据：`item1-params/main-<jdk>.json`、`item1-params/variation-<jdk>-<a~g>.json`（jdk8、jdk17）。

| 参数 | 结果（JDK 8/11/17/21 一致） |
|---|---|
| `telnetPort=-1` | 3658 端口没有监听；只新增 HTTP 监听 |
| `httpPort`、`ip=127.0.0.1` | 新增一个 IPv4 回环监听（以 `::ffff:127.0.0.1` 显示）；从宿主机访问容器 IP:端口被拒绝 |
| `password` + `localConnectionNonAuth=false` | 无凭证和错误凭证返回 401，正确凭证返回 200 |
| `disabledCommands` | 列表内的命令（`ognl`、`watch`、`redefine`、`vmtool`、`options` 等）返回 `<命令>: command not found`；列表外的命令正常执行 |
| `sessionTimeout` | 生效，见项 4 |
| `mcpEndpoint=` | 见下方变体 a、b、c |

变体：

| 变体 | 条件 | 结果 |
|---|---|---|
| a | 包内是 Arthas 自带的 `arthas.properties`，使用计划 3.1 的全部参数（含 `mcpEndpoint=`） | `/mcp` 带认证返回 400（MCP 服务在运行），不带认证返回 401。`mcpEndpoint=` 没有关闭 MCP，原因未查明 |
| b | 同 a，但不传 `mcpEndpoint` | 同 a |
| c | 自带属性文件，只传 `httpPort=18563` | 3658 端口监听 telnet，HTTP 无认证，`ognl` 无需认证即可执行；`/mcp` 无认证返回 400 |
| d | 设置 `password`，不设 `localConnectionNonAuth=false` | 本机连接仍免认证（无凭证返回 200）。必须同时设置 `localConnectionNonAuth=false` |
| e | 密码含 `+`、`%41` | agent 参数整体经 URL 解码（`+`→空格，`%41`→`A`），按字面密码认证返回 401，按解码后的密码返回 200。密码使用字母和数字 |
| f | 不设 `disabledCommands` | 所有命令可用（对照 `disabledCommands` 的效果） |
| g | 包内没有 `logback.xml` | Arthas 向目标进程的 stdout 打印 DEBUG 日志（62 行）和 `[ERROR] can not find arthas logging config`。包内必须带 `logback.xml` |

删除 `arthas.mcpEndpoint`、`arthas.mcpProtocol` 两个键后的属性文件：`/mcp` 返回 404（MCP 服务未启动）。计划第 6 节已写“删除 `mcpEndpoint`”，实测确认这一步必需，并且 `mcpProtocol` 也要删除。

密码泄露检查：在目标容器的 `/home`、`/tmp`、`/app`、`/logs`、`/root`、`/var/tmp` 全部文件、`docker logs`、JVM 日志文件、`/proc/<pid>/` 的 cmdline、environ 和 attach 套接字相关信息中搜索密码字面值，均未发现。计划第 10 节“用户指定的密码在这段代码中不写日志”的判断与实测一致。

### 3.2 项 2：只有 JRE 的镜像能否运行 arthas-core

方法：`jre8`、`jre17`、`jlink17` 镜像中用 `ja-attach` 从容器外部 attach，执行 L1 命令。

原始数据：`item2-jre/result.json`。

| 镜像 | 主机端 attach | L1 命令 | 方案 A（`java -jar arthas-boot.jar`） |
|---|---|---|---|
| JRE 8 | 成功（`libinstrument.so` 存在） | `version`、`jvm`、`memory`、`dashboard -n 1`、`thread -n 5`、`thread -b`、`sc -d`、`sm -d`、`classloader -t/-l`、`logger`、`sysprop`、`session` 全部成功 | 失败：`Can not find tools.jar` |
| JRE 17 | 成功 | 同上，全部成功 | 失败：`NoClassDefFoundError: com/sun/tools/attach/AgentLoadException` |
| jlink 17（不含 `java.instrument`） | 返回 `-1 java.lang.module.FindException: Module java.instrument not found`；目标继续服务，没有线程转储 | — | — |

JRE 镜像没有 `libattach.so` 和 `jdk.attach` 模块。HotSpot 的 attach 监听器在目标进程内，不依赖它们；主机端按 attach 协议直接与目标通信，因此 JRE 镜像可用。

检测 `java.instrument` 缺失：`<JAVA_HOME>/lib/libinstrument.so`（JDK 8 为 `lib/amd64/libinstrument.so`）不存在，或 `release` 文件的 `MODULES` 不含 `java.instrument`。

### 3.3 项 3：stop 后的回收；50 次 attach/stop

方法：每个 JDK 容器（内存限额 4 GB，堆 512 MB）：基线快照 → attach → stop → 50 次 attach/执行 `version`、`thread`/stop 循环 → 快照 → 两次类直方图（各触发一次 Full GC）→ 快照 → 额外 2 次 `jcmd GC.run`（Full GC）→ 快照。

原始数据：`item3-stop/<jdk>.json`（内存限额 4 GB）；`item3-stop-1g-oom/<jdk>.json`（内存限额 1 GB，容器被 OOM killer 结束时中止）。本节全部数值来自最终提交的脚本重跑的结果。更早的一次运行（`../earlier-runs/functional-before-final/item3-stop/`，脚本相同）见本节末尾的对照。

单次 attach 后停止：

| 指标 | JDK 8 | JDK 11 | JDK 17 | JDK 21 |
|---|---|---|---|---|
| stop 后监听端口关闭用时 | 3.1 秒 | 3.1 秒 | 3.2 秒 | 3.1 秒 |
| Arthas 线程（`arthas-*`）：attach 期间 → stop 后 | 18 → 0 | 18 → 0 | 18 → 0 | 18 → 0 |
| 50 次循环中端口关闭用时最大值 | 3.2 秒 | 3.2 秒 | 3.2 秒 | 3.2 秒 |
| 50 次循环中 attach 成功次数 | 50 | 50 | 50 | 50 |

`stop` 的 HTTP 请求返回 `unexpected EOF`（服务端先关闭连接再应答），按成功处理，并用端口和线程确认。

50 次循环的元空间和内存（MB）：

| 指标 | JDK 8 | JDK 11 | JDK 17 | JDK 21 |
|---|---|---|---|---|
| 基线（元空间使用量） | 61.6 | 61.7 | 59.4 | 61.4 |
| 第 1 次循环后 | 92.2 | 94.7 | 92.2 | 94.9 |
| 每次循环增量：相邻两次循环的中位数 | 12.1 | 12.7 | 12.4 | 12.6 |
| 每次循环增量：第 1→50 次的平均（含下行的 GC 卸载） | 10.3 | 11.2 | 10.1 | 10.0 |
| 50 次循环中使用量下降的次数（每次下降量，MB） | 2（24.5、36.1） | 2（0.4、51.0） | 2（0.4、86.4） | 2（0.3、100.4） |
| 第 50 次循环后 | 598.6 | 642.1 | 587.3 | 586.3 |
| 第 2 次 Full GC 后（使用量） | 394.0 | 388.0 | 303.7 | 335.2 |
| 第 3 次 Full GC 后（使用量） | 68.9 | 70.3 | 69.1 | 71.4 |
| 第 3 次 Full GC 后（提交量 committed） | 230.8 | 231.8 | 78.5 | 81.1 |

| 基线 cgroup 内存；第一次 attach 的增量 | 590；+59 | 580；+78 | 535；+110 | 628；+88 |

"Full GC"的来源：第 50 次循环后用 `jcmd GC.class_histogram` 做两次类直方图（各触发一次 Full GC，间隔 3 秒），再用 `jcmd GC.run` 额外执行 2 次，共 4 次。第 3 次、第 4 次之间元空间使用量不再变化（JDK 8 68.900 → 68.903 MB）。JDK 8 的类加载器数量来自类直方图中的 `ArthasClassloader` 实例数，因为 `jmap -clstats` 在 JDK 8 失败。每次循环的快照中，下降的两次都伴随 GC 次数增加和类卸载（卸载 1930~16510 个类），GC 的触发原因未记录。

结论：

- stop 后线程和端口回收。类加载器不会随 stop 立即回收：50 次循环后做第 1 次 Full GC 时仍有 19~27 个 `ArthasClassloader`，第 2 次 Full GC 后全部卸载。
- 每次 attach/stop 使元空间使用量增加约 12.1~12.7 MB（相邻两次循环的中位数；每次 attach 加载约 3000~3200 个类）。50 次循环中，使用量各下降 2 次（GC 卸载了类），所以第 1→50 次的平均增量为 10.0~11.2 MB。3 次 Full GC 后使用量回到基线 +7.3~+10.0 MB，其中包含常驻的 arthas-spy 类（位于 bootstrap 类路径，无法卸载）。
- JDK 8、11 的元空间提交量在 Full GC 后仍为 231~232 MB，没有归还给操作系统；JDK 17、21 为 79~81 MB。cgroup 内存在 Full GC 后保持在 1.10~1.37 GB（基线 0.54~0.63 GB），比基线高 0.51~0.79 GB。
- 每次循环使 cgroup 内存增加：相邻两次循环的中位数 16 MB（JDK 8）、27 MB（JDK 11）、27 MB（JDK 17）、26 MB（JDK 21）。
- 没有设置 `MaxMetaspaceSize` 的 JVM 不会因元空间增长而报 `OutOfMemoryError: Metaspace`，增长由容器内存限额约束：内存限额 1 GB 的容器（堆 512 MB）在完成 25 次（JDK 8）、17 次（JDK 11）、16 次（JDK 17）、14 次（JDK 21）循环后，在下一次循环中被内核 OOM killer 结束（退出码 137，`OOMKilled=true`）。记录见 `item3-stop-1g-oom/`。
- 线程数：50 次循环后 22~24，基线 20~22，没有线程泄漏。
- 与更早一次运行（脚本相同）的差异：该次运行的第一次 attach 的 cgroup 增量为 +77、+102、+101、+102 MB（JDK 8、11、17、21），本次为 +59、+78、+110、+88 MB（相差 9~24 MB）；该次 4 次 Full GC 后的使用量为基线 +8~+20 MB，本次为 +7~+10 MB（JDK 8 该次为 81.0 MB，本次 68.9 MB）；该次的 1 GB 限额容器在 10~25 次循环时被结束。同一脚本两次运行之间，第一次 attach 的 cgroup 增量和 OOM 时的循环次数都有差异，原因未查明。
- 文件描述符和内存映射的残留见项 7。

### 3.4 项 4：会话超时或 HTTP 连接断开后，增强作业是否终止、增强代码是否还原

方法：示例应用持续接收 `/hot` 请求，用探针（计数 spy，不触发 retransform）读取 `demo.HotService` 是否仍被增强；JDK 9+ 用 `-Xlog:redefine+class*` 记录，JDK 8 用探针 agent 的 retransform 日志。`sessionTimeout=20` 秒。会话用 `init_session` 创建，作业用 `async_exec` 启动。

原始数据：`item4-session/<probe8|jdk11|probe17|jdk21>.json`（第 1 轮）、`...-round2.json`（第 2 轮）、`probe8|probe17-round2-mn.json`（恢复验证）。第 1 轮的场景 d（客户端不再访问）和 e（空闲会话）在等待期间轮询了 `session_info`，轮询刷新了会话的访问时间，结果无效；第 2 轮（场景 d2、e2）改为等待期间不访问会话，下表使用第 2 轮的结果。

| 场景 | 结果（JDK 8/11/17/21 一致） |
|---|---|
| e2：创建 3 个空闲会话（`sessionTimeout=20`），分别在 30、65、130 秒访问 | 30 秒仍存在；65、130 秒返回 `session not found`。会话在超时后由周期为 60 秒的清理线程回收，最长约 20+60 秒 |
| d2：`async_exec` 启动 `watch ... -n 5`（条件永不满足），150 秒不访问会话 | 会话仍存在，作业继续运行，类保持增强。`sessionTimeout` 不终止正在运行的作业 |
| `watch -n 3` 自行结束 | 作业结束，类**仍被增强**；`reset` 后还原 |
| `execTimeout`（5 秒）到期 | 作业状态为 `INTERRUPTED`，类**仍被增强**；`reset` 后还原 |
| 同步 `exec` 期间 HTTP 客户端被 `kill -9` | 作业**继续运行**到 `execTimeout` 到期，期间同一会话拒绝新命令（`Another job is running.`）；到期后类仍被增强 |
| `close_session` 关闭运行作业的会话 | 作业被中断，类**仍被增强** |
| `reset` 在作业运行期间执行 | 返回成功，但类**仍被增强**，Arthas 不再记录该类；之后 `reset demo.HotService` 无效果 |
| `stop` 在作业运行期间执行 | 服务端关闭，类**仍被增强**，spy 切换为 Nop；重新 attach 后也不会还原 |
| 作业结束或关闭会话后 `reset` | 类还原 |
| 作业结束后 `stop` | 类还原，spy 切换为 Nop |

`Enhancer.reset` 只遍历 Arthas 记录的已增强类（`classBytesCache`）并 retransform 这些类，因此作业运行期间的 `reset` 使类留在增强状态且失去记录（已用 `javap` 反编译核对，并由探针日志验证）。

JDK 8 的重跑中，第一次执行场景 b 时 `watch` 没有增强目标类（`classCount` 为 0，作业在 267 ms 内 `SUCCEEDED`），该次结果保存为 `item4-session/probe8-run1-watch-not-enhanced.json`，不用于上表；单独重跑 probe8 得到有效结果，与上表一致。第一次未增强的原因未查明。

恢复方法（JDK 8、17 均验证）：对该类再执行一次 `watch ... -n 1`（Arthas 重新记录该类），再执行 `reset`，类还原；`stop` 后残留增强的恢复方法相同：重新 attach，再执行 `watch ... -n 1`，再执行 `reset`。

对计划 3.3、3.4 的影响：

- 清理顺序必须是“中断作业并关闭会话 → `reset` → `stop`”。作业运行期间执行 `reset` 会使增强残留。
- `sessionTimeout` 不能作为 allowops-exec 异常退出后的回收手段：运行中的作业不受它影响。主机端残留回收需要使用会话记录中的密码重新连接，执行 `close_session`、`reset`，再 `stop`。
- allowops-exec 被 SIGKILL 结束后，HTTP 连接断开不会终止作业；作业持续到 `execTimeout` 到期，类保持增强，直到回收流程执行 `reset`。所以每条 L2 命令的 `execTimeout` 必须设置，并作为最大残留时间。

### 3.5 项 5：attach、L1、L2 对 p99 的影响，retransform 停顿

#### 3.5.1 方法

- 每个场景使用新启动的容器和 JVM。预热 60 秒后依次是三个各 60 秒的窗口：前（没有 Arthas 调用）、中（Arthas 调用）、后（Arthas 已 stop；中窗口和后窗口之间间隔 8 秒）。
- JVM：容器 CPU 固定为 4~7（4 个 CPU），堆 512 MB，G1，容器内存限额 2 GB。压测进程固定在 CPU 8~9，`nice -10`。
- 负载：开环压测（固定到达率，延迟从请求被调度的时刻起算）。`hot` 流 1000 请求/秒，每个请求调用被观察方法 `demo.HotService.work` 1 次（配置 `p1k`：被观察方法 1000 次/秒）或 10 次（配置 `p10k`：10000 次/秒）；`ping`、`work`（CPU 计算）、`db`（H2 查询）三个对照流各 300 请求/秒，不调用被观察方法。被观察方法耗时约 1 微秒。
- 场景（中窗口内的动作）：

| 场景 | 动作 |
|---|---|
| `noop` | 无。用于测量噪声 |
| `attach_cycle` | 重复“attach、stop、暂停 2 秒” |
| `attach_hold` | attach 一次，空闲约 57 秒，stop |
| `l1c:<命令>` | 重复“attach、执行 L1 命令、stop、暂停 2 秒”（产品中一次 L1 调用的形态） |
| `l1s:<命令>` | attach 一次，每秒执行一次 L1 命令，最后 stop（同一会话内重复执行） |
| `l2:<watch\|trace\|stack\|monitor>` | attach；两次约 27.5 秒的增强作业，每次作业后 `reset`；stop |
| `l2keep:watch` | 同 `l2`，但作业结束后不 `reset`、不 `stop`，类保持增强到后窗口结束，Arthas 仍在运行 |

- 指标：
  - 请求延迟的 p50、p99、p99.9、最大值，来自对数直方图（相邻桶之比 1.01）。
  - “合并 p99”：窗口内所有请求的 p99。“典型 p99”：窗口内每秒 p99 的中位数，单次停顿不影响它。
  - “p99 增幅”及 95% 置信区间：对窗口内的秒有放回重采样 300 次，比较合并 p99。
  - 每秒的 JVM 进程 CPU、JVM 线程处于可运行但未获得 CPU 的时间（`/proc/<pid>/task/*/schedstat`）、CPU 4~7 上其他进程占用的 CPU（`/proc/stat` 的忙碌时间减去容器 CPU 用量，100% 为一个 CPU）。
  - JVM 的 GC 日志和安全点日志（JDK 9+ `-Xlog:safepoint*`；JDK 8 `-XX:+PrintSafepointStatistics`）。
  - “调用相关秒”：attach、命令、reset、stop 所在的秒，加上每个作业的前 3 秒。“作业秒”：作业的其余秒。“其余秒”：中窗口内的其他秒。
- 覆盖：59 次运行。JDK 17：35 次（全部场景，其中 `noop` 4 次、`attach_hold` 3 次，其余场景 1~3 次）；JDK 8：8 次；JDK 11、21：各 8 次（`noop`、`attach_cycle`、`l1c:thread -b` 各 1 次，`l2:watch@p10k` 5 次）。
- 错误率：59 次运行共 29 370 141 个请求（含预热和窗口间隔），错误 0，丢弃 0，最长延迟 4.15 秒（JDK 11 `l2:watch@p10k` 重复 4，见 3.5.6；超时设置为 5 秒）。

原始数据：`bench/<jdk>/<场景>__<配置>/rep<k>/`（`load.jsonl` 每秒每个流的直方图，`metrics.jsonl` 每秒指标，`calls.jsonl` 每次 Arthas 调用的起止时间，`gc.log`、`safepoint.log`、`redefine.log`、`stdout.log`）；汇总表 `bench/summary.md`；本节表格 `bench/report-tables.md`、`bench/transitions-table.md`。生成方式：`scripts/analyze.py <bench> --md`、`scripts/transitions.py --table <bench>`、`scripts/report_digest.py`、`scripts/l2_stats.py`。

#### 3.5.6 整个 JVM 的暂停

“JVM 暂停”：同一时段内 JVM 的所有线程没有进展，所有接口（含未被观察的接口）的请求同时延迟 0.2 秒以上。它不同于 3.5.5 的增强开始瞬态：瞬态期间 JVM CPU 为 178%~378%，暂停期间 JVM 进程累计 CPU 时间接近 0。

**观察**

- 59 次运行中有 3 次出现 JVM 暂停：JDK 11 `l2:watch@p10k` 重复 1、重复 4，JDK 21 `l2:watch@p10k` 重复 1。JDK 11 重复 2、3、5，JDK 21 重复 2~5，以及 JDK 17（6 次 10000/秒的 L2 运行）、JDK 8（1 次）的 10000/秒 L2 运行中没有。

**结论**

- JVM 暂停是事实：3 次运行中 JDK 11 有 20 个、JDK 21 有 2 个安全点事件，延迟 0.03~4.12 秒，影响所有接口。
- 暂停的原因未查明。已观察到的现象：（1）JDK 11 的 20 个事件中 5 个发生在 `stop` 返回之后，此时没有 Arthas 作业；（2）JDK 11 重复 1 的一个暂停与 k3s 慢 SQL 同时出现，重复 4 的两个暂停与系统日志间隔同时出现；JDK 21 重复 1 没有可对照的记录；（3）加 `--tripwire` 的 17 次 JDK 11 `l2:watch@p10k` 和 3 次 `noop@p10k` 中没有出现 200 ms 以上的无进展。
- 反例：主机上的停顿记录并不总对应 JVM 暂停。11 条其他运行期间的 k3s 慢 SQL、`fsync` 探测中 16 次 1 秒以上的耗时、`--tripwire` 进程的 2.22 秒无进展，都没有对应的 JVM 暂停。
- 未验证：主机停顿与 JVM 暂停之间的因果机制（没有捕获到暂停时阻塞线程的内核栈）；Arthas 的增强是否提高暂停的发生概率；暂停的发生频率（`bench.py` 的 10 次 JDK 11、21 `l2:watch@p10k` 运行中 3 次，加 `--tripwire` 的 17 次中 0 次）。
- 对阈值的影响见 5.1、5.3：JDK 11、21 上的 L2 命令可能遇到 0.2~4.2 秒的整个 JVM 暂停，这与增强开始瞬态无关。

### 3.9 附加：attach 文件位置、uid、`-Xrs`、PID 1、`DisableAttachMechanism`

原始数据：`item9-attach-files/matrix-<jdk>.json`、`matrix-root8.json`、`matrix-root17.json`、`special.json`。

attach 文件位置和 uid 矩阵（目标 JVM 以 uid 10001 运行；“文件属主”和“连接身份”各取 root 或目标 uid）：

| JDK | 目标工作目录或 `/tmp` 的 attach 文件，属主 root、连接 root | 属主目标、连接 root | 属主 root、连接目标 | 属主目标、连接目标 | 两处都无 attach 文件 |
|---|---|---|---|---|---|
| 8 | 失败：`socket did not appear` | 失败：连接被目标关闭（`write unix @->/tmp/.java_pid7.tmp: write: broken pipe` 或 `read ... connection reset by peer`，两次运行各出现一种） | 失败：`socket did not appear` | 成功 | 失败，目标 stdout 出现线程转储 |
| 11、17、21 | 成功 | 成功 | 成功 | 成功 | 失败，目标 stdout 出现线程转储 |
| 8、17，目标以 root 运行 | 全部成功 | 全部成功 | 全部成功 | 全部成功 | 失败，线程转储 |

- JDK 8 要求 attach 文件的属主和连接套接字的对端 uid 都等于目标进程的有效 uid。allowops-exec 以 root 运行，在 JDK 8 目标上必须创建属主为目标 uid 的文件（`fchown`），并以目标 uid/gid 连接套接字（`setuid`/`setgid`，位于锁定的 OS 线程）。JDK 11+ 接受 root。
- 没有 attach 文件时 SIGQUIT 触发线程转储，输出到目标进程的 stdout。这是副作用，pre-check 必须保证至少一个 attach 文件位置可写后再发信号。
- 套接字固定是 `/tmp/.java_pid<nspid>`。attach 文件在 JDK 8/11/17/21 中先查目标工作目录再查 `/tmp`，两处任一存在即可。
- JVM 的 attach 监听器在第一次 attach 后一直存在；之后的 attach 可以直接连接已存在的套接字，不需要信号（`socket_reused`）。
- `-Xrs`：`SigCgt` 不含 SIGQUIT（`0x…1cc8`，正常为 `0x…5ccf`），JVM 启动时就创建 attach 监听器，直接连接套接字可以 attach。pre-check 的规则：`SigCgt` 不含 SIGQUIT 且套接字不存在时拒绝发信号（SIGQUIT 默认动作是终止进程）。
- PID 1：目标是容器内 PID 1 时，attach 成功（nspid 为 1）。
- `-XX:+DisableAttachMechanism`：hsperfdata 的 `sun.rt.jvmCapabilities` 首字符为 `0`（正常、JRE、jlink 均为 `1`）；attach 失败（`socket did not appear`）并在目标 stdout 产生线程转储。pre-check 必须在发信号前读取这个计数器。
- JDK 21 向目标 stdout 打印 `dynamic agent loading` 警告；JDK 17、21 打印 `Sharing is only supported for boot loader classes` 的 CDS 警告。

### 5.3 计划 3.3：运行期监测与 `execTimeout`

- CPU、健康检查延迟的中止阈值，在增强开始后的 5 秒内不评估。增强开始后 1~4 秒内 JVM CPU 达到 178%~378%，所有接口的延迟达到数百毫秒（3.5.5）；这段时间内评估阈值，每次增强开始都会触发中止。依据：实测。
- `execTimeout` 上限建议 60 秒。实测的作业为 2 次约 27.8 秒（4 个 JDK），更长的作业未测。依据：实测范围，上限为估算。
- 监测不能避免 3.5.6 的暂停：暂停期间 JVM 进程的 CPU 接近 0，CPU 阈值检查不会因暂停触发；健康检查请求在暂停期间同样延迟 0.2~4.2 秒，是否触发取决于健康检查的超时和阈值。暂停的原因未查明，Arthas 是否提高其发生概率未验证，本节的建议值没有为它调整。依据：3.5.6。

## 6. 局限

- 单机共享主机：其他会话的构建和测试同时在 CPU 4~9 上运行，延迟数据有噪声，见项 5 的噪声标定。主机上同时运行 k3s 和其他容器，存储曾出现 1 秒以上的 `fsync` 耗时（3.5.6）；JVM 日志写在主机的 bind mount 上。
- 示例应用约 12k 个类，热点方法约 1 微秒；类数量更多或方法更重的真实应用的元空间增量、retransform 时间、JIT 影响可能不同。
- 只测了 eclipse-temurin 构建；其他厂商的 HotSpot 构建（Zulu、Corretto、Dragonwell 等）和 OpenJ9 未测。OpenJ9 不是 HotSpot，计划 3.2 已将其排除。
- JDK 11、21 只做了功能性实测和项 5 的子集；JDK 8 的类加载器统计来自类直方图（`jmap -clstats` 在 JDK 8 失败）。
- 项 5 只测了 4 个 CPU 的容器、512 MB 堆、G1；CPU 更少或堆更大时增强开始瞬态的长度未测。L2 命令的条件永不成立，条件成立时输出和序列化的开销未测。
- 项 5 中 JDK 11、21 上整个 JVM 暂停的原因未查明，发生频率只有两个观测值：`bench.py` 的 JDK 11 运行 2/5、JDK 21 运行 1/5，加 `--tripwire` 的 JDK 11 运行 0/17；差异是否来自 `--tripwire` 本身未验证（3.5.6）。
- 未验证：可写根文件系统且用户没有 passwd 条目时的日志路径；MCP 服务在 Arthas 自带属性文件下的命令限制；`-XX:-UsePerfData`（没有 hsperfdata）的目标；Kubernetes、CentOS 7（内核 3.10）。
- 本报告的原始数据保存在执行实测的本地主机上，不在仓库中；部分运行使用提交前的脚本修改（见文首的验证版本）。
